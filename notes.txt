
MCP (Model Context Protocol)

	Models are only as good as the context provided to them. MCP is an open protocol that standardizes how your LLM applications connect to and work with your tools & data sources.

	Whatever can be done with MCP, can be done without MCP as well. 

	Example: (without MCP)

		AI App 1 -> Custom Implementation -> Custom prompt logic -> Custom tool calls -> Custom data access

		AI App 2 -> Custom Implementation -> Custom prompt logic -> Custom tool calls -> Custom data access

		// .. etc

	(with MCP)

		MCP Compatible LLM app -> Data Store MCP Server -> Databases / SQL, etc

		MCP Compatible LLM app -> CRM MCP Server -> CRM systems

		MCP Compatible LLM app -> Version Control MCP Server -> Version Control software

	Note: With MCP, not only is the AI app development strealimed because you will be able to talk to multiple systems, but even the MCP server themselves can be exposed to multiple different AI agents!

MCP Architecture

	MCP client and MCP server maintain 1:1 relationship, and communicate through messages defined in MCP protocol.

	A single host can contain multiple MCP clients which connect to disparate remote MCP servers.

	MCP Client responsibilities
	
		- Invokes tool (similar to tool calling for LLM's)
		- Queries for resources

			These can be files, DB records, or API responses (i.e. traditional API requests)

		- Interpolates prompts

			Instead of burdening users with complex prompt engineering techniques bespoke to different systems (like google-drive, a PDF, etc), the server maintains and exposes prompt templates which the client can fill in. The client in turn requests the data to fill-in by the user, but the overhead of management is delegated to MCP

	MCP Server responsibilities

		- Exposes tools
		- Exposes resources
		- Exposes prompt templates

MCP Python SDK for writing MCP server:

	Defining tools

		@mcp.tool()
		def add(a: int, b: int) -> int:
		"""
			// description of arguments
		"""
		// business logic
		return a + b

	Defining resources (just like defining GET and POST requests on a server)

		@mcp.resource(
			"docs://documents", // you can templatize it as well
			mime_type="application/json"
		)
		def list_docs()
			// business logic

	Defining prompts

		@mcp.prompt(
			name="format",
			description="Rewrites the contents of a document in markdown format"
		)
		def format_document(
			doc_id: str
		) -> list[base.Message]:
			// business logic, i.e., the highly complicated prompt

		Note: If we were to leave the prompt engineering to the user, they may instantly write:

			"Convert report.pdf to mardown"

		However, if they had access to prompt templates, as we defined above, then the user just has to supply arguments to the prompt template and the LLM gets sufficient information to accomplish the task

Transport between MCP client & server

	If both clients and server are running locally then use "stdio", i.e., the client launches the server as a subprocess! When we are using the SDK, everything happens behind the scenes.

	Else, use:

		- HTTP + SSE (Server Sent Events)

			This is a stateful connection.

		- Streamable HTTP [MOST RECOMMENDED]

			Can be stateful/stateless.

Upcoming features of MCP

	- Authentication

		Sometimes server needs to access information which requires authn/authz

	- Roots

		Client can specify the server the roots where it needs to look for resources

	- Sampling

		Server requests inference from the LLM (instead of client requesting it). 

	- Registry API
	
		Unified way to discover MCP servers. Allows for trust, similar to DNS.

MCP server for production-incident-evidence:

	| Primitive  | Example 														| Purpose 								   |
	|------------|--------------------------------------------------------------|------------------------------------------|
	| Tool 	     | `search_incidents(query, service, version, limit)`           | Execute a search 						   |
	| Tool       | `get_deployment_diff(deployment_id)`                         | Retrieve a focused deployment comparison |
	| Resource   | `runbook://payments/idempotency` 							| Read identifiable context 			   |
	| Prompt     | `investigate_payment_failure(error_code, service)`           | Obtain a reusable investigation template |

	Tools are executable operations, resources expose readable context, and prompts supply templates. A resource is not simply another spelling of a REST GET endpoint; its URI and metadata form a context interface.

	A resource supplies evidence. A prompt supplies instructions for working with evidence. Neither automatically invokes an LLM.

	Workflow

		User request
			↓
		Host exposes relevant tool schemas to the model
			↓
		Model proposes search_incidents(...)
			↓
		Host validates and authorizes the operation
			↓
		MCP client sends tools/call
			↓
		MCP server queries search backend
			↓
		Structured evidence returns to the host
			↓
		Host supplies evidence to the model

	An illustrative result should be compact and useful:

		{
			"matches": [
				{
				"incident_id": "inc_1842",
				"summary": "Retry reused an idempotency key with a modified payload.",
				"service_version": "3.8",
				"evidence_uri": "incident://inc_1842"
				}
			],
			"next_cursor": null
		}

	Note: Current MCP list/read responses include caching metadata; avoid assuming every tool result is cacheable or safe to share across users.

	Example of resources in MCP

		Simple Example (static resource)
		
			@mcp.resource(
				"runbook://payments/idempotency",
				mime_type="text/markdown",
			)
			def payment_idempotency_runbook() -> str:
				"""Explain the payment service's idempotency and retry behavior."""
				return """
			# Payment idempotency

			- Retrying a request must preserve its idempotency key and payload.
			- Reusing the key with a changed payload produces PAYMENT_4027.
			- Check the original request and retry payload before diagnosing.
			"""

		More practical example

			def payment_idempotency_runbook() -> str:
    			return document_store.read("payments/idempotency.md")

		The URI is an identifier understood by this MCP server. It need not be a public URL or a filesystem path. When a client reads it:

			# Assume client is already connected.
			resource = await client.read_resource(
				"runbook://payments/idempotency"
			)

		Full workflow:

			Host application
				↓ resources/read(uri)
			MCP server executes the registered resource function
				↓
			Returns runbook content and metadata
				↓
			Host decides whether to include it in the model's context

		Exposing multiple resources with templating:

			@mcp.resource(
				"runbook://{service}/{topic}",
				mime_type="text/markdown",
			)
			def read_runbook(service: str, topic: str) -> str:
				return document_store.read_runbook(service, topic)

			Usage:

			await client.read_resource("runbook://payments/idempotency")

	Examples of Prompts in MCP

		@mcp.prompt()
		def investigate_payment_failure(error_code: str, service: str) -> str:
			"""Create an evidence-based payment investigation prompt."""
			return f"""
		Investigate error {error_code} in service {service}.

		1. Establish the error's meaning from the applicable runbook.
		2. Compare affected requests with the documented requirements.
		3. Inspect relevant configuration and deployment changes.
		4. Separate confirmed facts from hypotheses.

		Return:
		- Likely cause
		- Supporting evidence and references
		- Missing information
		- Recommended next diagnostic step

		Do not invent evidence or modify production configuration.
		"""

		The function builds a prompt, rather than performing the investigation. A host might expose it as a menu entry or slash command:

		/investigate_payment_failure
			error_code: PAYMENT_4027
			service: payments

		Usage of above prompt:

			prompt = await client.get_prompt(
				"investigate_payment_failure",
				arguments={
					"error_code": "PAYMENT_4027",
					"service": "payments",
				},
			)

	End-to-End example of using resources and prompts in MCP

		runbook = await client.read_resource(
			"runbook://payments/idempotency"
		)

		investigation = await client.get_prompt(
			"investigate_payment_failure",
			arguments={"error_code": "PAYMENT_4027", "service": "payments"},
		)

		messages = [
			application_system_message,
			*convert_prompt_messages(investigation.messages),
			context_message(extract_resource_text(runbook)),
			user_message("Failures began immediately after yesterday's rollout."),
		]

		answer = await model.invoke(messages)
		
	Performance optimization solutions for various MCP concerns

		| Concern 								| Practical technique 												  |
		|---------------------------------------|---------------------------------------------------------------------|
		| Too many tool definitions 			| Select relevant tools instead of supplying an entire catalog 		  |
		| Huge tool outputs 					| Summaries, pagination, projections, resource references  		  	  |
		| Repeated discovery 					| Cache according to supported TTL/scope and invalidate appropriately |
		| Slow downstream I/O 					| Async calls, pooled connections, bounded parallelism 				  |
		| Expensive searches 					| Indexed filters, result limits, query budgets 					  |
		| Rate-limited APIs 					| Backpressure, quotas, bounded retries with jitter 				  |
		| Repeated writes after timeouts 		| Idempotency keys and durable operation records 					  |
		| Long operations 						| Durable handles, status retrieval, cancellation where supported 	  |
		| Difficult debugging 					| Spans around MCP calls and downstream operations 					  |
		| Contract drift 						| Versioned schemas and compatibility tests 						  |

	Design choices

		- Expose purposeful tools. search_incidents is easier to constrain than execute_arbitrary_sql.
		- Separate credentials. A token for your MCP server is not automatically valid for its downstream CRM or database. Audience validation and avoiding token passthrough are important protocol requirements.
		- Treat outputs as data. A retrieved document can contain misleading instructions; being returned by a tool does not grant it authority.
		- Handle ambiguous outcomes. A timeout after a write may mean the write succeeded. Blind retries can duplicate effects.
		- Keep stdio clean. Write diagnostic logs to stderr; stdout carries protocol messages.
